Part 1

Objective and deliverables

A configuration-aware test-generation framework for RISC-V, driven by the upstream Sail model, focused on the privileged architecture, and integrated into the Golden Model's continuous integration (CI).
 Deliverable
1Repository with the framework, user documentation and developer documentation — github.com/10x-Engineers/riscv-test-generation
2Example scripts that generate a test suite from a given Sail model configuration
3Example scripts that execute a suite, collect results and produce a summary
4CI integration into the Golden Model
5Pull requests for any Golden Model changes the framework requires

What we are building

The framework uses the Sail model as the executable reference for generation, validation and coverage. Routing is by extension. Floating point and Vector route to the Concrete Oracle; every other extension routes to ISLA, which symbolically executes the model and uses the Z3 SMT solver to derive the operands that reach a chosen behaviour. A small template backend handles branch and jump cases that require explicit construction.

Because floating point and Vector are deferred, the Oracle leg generates no tests in this project. Its job here is to read the model’s branch structure, derive the configurations it implies — PMP, PMA, exceptions, interrupts, translation — and emit the assembly that sets each one up. That setup code is embedded in the object emitter.

Generating one test takes both legs. The scenario goes to the emitter as flags, ISLA solves the operands, and the emitter writes one program: setup code, the instruction, the expected result. It runs on Sail and on Spike and the results are compared. Coverage from the instrumented model returns the missing scenarios to the generation engine, which derives a case for each.

A control layer runs the same loop for every configuration.

Part 2 · Methodology

The framework end to end

The method is one loop, run separately for each committed configuration. The Sail model is the only source of truth in it: the same model supplies the instruction inventory, the machine states worth reaching, the paths the solver reasons about, and the coverage targets everything is measured against.

The model is read twice, by different means, and the readings meet at the object emitter. One leg reads its branch structure and turns it into configurations and the assembly that sets them up. The other compiles it to an intermediate representation (IR) and solves for the operands that drive an instruction down a chosen path.

The same loop, component by component. Each arrow says what is handed to the next stage, which is where the two routes differ: the symbolic route passes constraints to a solver, the concrete route passes a program to the model and reads the answer back.

What follows takes the loop in order: how a target is routed, how privileged machine state is constructed, and how a test is executed, validated and measured.

Maintenance follows from the model being the source. The instruction inventory, the machine states worth reaching and the coverage denominator are all derived from the Sail model, so a change to the model changes all three. No table in the framework is hand-edited when an instruction is added.

Routing, by extension

The route is decided by which extension a target belongs to, not case by case.

Extension groupRouteWhat that route contributes
F, D, Zf*, Zd*, Zh*Concrete Oracle Test generation by observation. Deferred, so not exercised in this project
V, Zv*, vector cryptoConcrete Oracle The same, and for the same reason
Branch and jumpTemplate backend An explicit control-flow structure neither engine constructs. Capped at four builders; growth in that number is a defect signal
Every other extensionISLA Operand derivation — the values that make the instruction take a chosen path
Privileged machine state
PMP, PMA, traps, interrupts, translation		 Oracle leg, into the emitter Configuration derivation and the setup assembly for it, embedded in the object emitter and selected by flag
The two legs are not alternatives for a single test. A privileged test uses both: the Oracle leg supplies the configuration and the code that establishes it, ISLA supplies the operands of the instruction under test, and the emitter writes the two into one program.

Why the routing falls this way

Not preference — the symbolic engine cannot represent two extension groups, and the concrete leg has a second job that only it can do.

PropertyConsequence for routing
Reaches a named target on purposeThe route of choice when a specific model behaviour must be exercised
Proves unreachabilityAn UNSAT result justifies an exclusion from the coverage denominator
No FP arithmeticSoftFloat is external C with no body in the IR, so it cannot be executed symbolically. FP routes to the Oracle
Bounded bitvector widthVector state at VLEN 256 and 512 exceeds the engine's fixed-width representation. Vector routes to the Oracle
Operands, not machine stateThe solver derives operands; privileged state is constructed by the generator — see Part 3
One solve per testSuited to targeted work, not to bulk generation across all seven configurations

The Oracle leg’s two roles

RoleWhat it doesUsed here?
Test generation for FP and Vector Runs the instruction on the model, records the resulting architectural state, and uses that observed state as the expected result Not actively. The capability exists and works; floating point and Vector are deferred, so this leg generates no tests in this project
Configuration and scenario setup Reads the branch structure of the model, derives the configurations it implies for PMP, PMA, exceptions, interrupts and translation, and emits the assembly that establishes each one Yes — this is its job here. The setup code it produces is embedded in the object emitter
Why the same leg does both. Each role needs the model executed rather than solved — one to observe a result, the other to establish a machine state. Neither is something the symbolic engine can do, which is why they share a side even though only one is in scope.

How privileged scenarios are constructed

Privileged coverage comes from constructing the required machine state in the test preamble, not from selecting special instructions. The solver derives operands; the generator writes the control and status registers (CSRs), page tables and privilege transitions directly.

GroupHow the state is constructed
Privilege modesConfigure the privilege state, then enter it with the appropriate return instruction
CSRsAccess legal registers at the appropriate privilege level
TrapsConstruct the faulting condition, then verify the trap cause and its origin
InterruptsConfigure pending, enable and delegation state
Virtual memoryConstruct page tables and configure satp
PMPConfigure entries, then make permitted and denied accesses
PMASelect a platform configuration whose region attributes produce the case, then make the access
PMP and PMA differ only in where the configuration comes from. PMP is written by the test into CSRs; PMA is a per-region attribute in the model’s configuration file — so a PMA test needs only a configuration and an access.

Deriving cases from the model

Privileged features are not instructions, and their case list is not something to write by hand. It is derived in two stages.

 StageWhat it does
1Case extractionThe Oracle leg reads the deciding functions in the Sail sources — the enumerations, bitfields and match arms — and writes out a case file. It reads the model and runs nothing
2Case executionThe case is passed to the emitter as flags. The emitter writes the setup code for that case, ISLA solves the operands of the instruction, and the two go into one program

The object writer is ISLA’s RISC-V emitter, and the single place that turns a case into a program. It emits every part of the test; the case flags decide only the state-building step.

What it emitsContents
The preambleThe trap vector first, then the machine state the case calls for — PMP entries, page tables, delegation and interrupt state, mstatus bits — then the transition into the privilege the case runs in
The page tableWritten into the data section when the case needs translation, with the entries the case specifies
The instruction under testRaw encoding bytes, with the operands ISLA solved for. Emitting the encoding rather than a mnemonic keeps the test on the exact encoding the model decoded
The expected stateRegister and memory tables compiled in as data, which the test compares itself against
The trap handlerThe cause check, the origin check, and the report-from-handler path a violation test needs
The reporting codeThe HTIF write that ends the run and carries the verdict
The linker scriptEvery section pinned at a fixed, non-overlapping address
Only the state-building step varies. The handler, the comparison, the reporting and the linker script are identical in every test, so a new case changes what the preamble programs and nothing else.

ISLA is not bypassed here. It still solves the operands of the instruction under test. The case supplies the state around it, which the solver cannot derive — nothing in the model asks for a PMP entry to be placed anywhere.

The five privileged paths

All five derive their cases the same way. They part company at the point of application: four program their state from inside the test, while a memory attribute is a property of the platform and can only be chosen by picking the configuration.

FeatureWhat the extractor readsHow the state is appliedWhat the test checks
PMP The address-match modes, the configuration bitfield, the range comparisons, the permission arms, and the rule that legalises a configuration write Preamble writes to the pmpaddr and pmpcfg registers The access is permitted, or faults with the expected cause
Translation The satp mode decoding, the PTE flag bitfield, the invalid-PTE disjuncts, and the three permission gates A page table into the data section, then satp, sfence.vma, and the drop to Supervisor The address translates, or raises the expected page or access fault
Exceptions The exception cause mapping, the rule that decides when a trap value is written, and the delegation legaliser The preamble sets delegation and privilege; the test region holds the faulting instruction The cause register, and which mode took the trap
Interrupts The interrupt cause mapping, the priority order the model checks in, which bits are undelegatable, and which are writable Preamble writes to the pending, enable and delegation registers, and the global enable Which interrupt is taken, and at which privilege
PMA The region attributes the platform configuration declares Not applied by the test. The configuration is selected before the run The access is permitted, or faults, according to the region's attributes
PMA is the one path not yet built. The other four are implemented. It needs no new generator capability — every attribute is already a field in the model’s configuration — so it is a configuration exercise, not a generator one.

A worked example: a load denied by PMP

One case, end to end — generated, run on both simulators, and measured. Every figure below came from this run.

1 · Generate

The case names the PMP state and the expected outcome; the solver fills in the operands.

isla-testgen -A riscv-ir/riscv64.ir -C riscv-ir/riscv64.toml -a riscv64 \
  --memory-region 0x80020000-0x80030000 -o lw_pmp_read_denied -n 1 \
  0x80020137 0x02011113 0x02015113 0x00012083 \
  --pmp-deny 0x80020000 --expect-trap-cause 5 --trap-is-pass

The last opcode is the lw under test. The three flags say what state to build, what should happen, and that the trap is the result.

2 · What the emitter writes

The preamble programs two PMP entries before the test region begins: entry 0 denies the region under test, entry 1 permits everything else. PMP is first-match, so the denying entry has to be entry 0 — reversed, the catch-all matches first and the test would pass while proving the opposite.

csrw pmpaddr0, x31        /* the denied region */
li   x31, -1
csrw pmpaddr1, x31        /* catch-all */
li   x31, 0x1f98          /* [0] = locked NAPOT, no permissions; [1] = NAPOT, RWX */
csrw pmpcfg0, x31
j    test_start
3 · Run on both, and compare
RunCommandResult
Sail modelsail_riscv_sim --config rv64d_v128_e64.json lw_pmp_read_denied.elfSUCCESS
Spikespike --isa=rv64imac_zicsr lw_pmp_read_denied.elfpass, exit 0
Negative controlspike --isa=rv64imac_zicsr NEG_wrong_cause.elfFAILED, exit 1 — as it must
The negative control is the part that matters. The same test with the expected cause changed fails. Without it, a passing run tells you nothing: a test that cannot fail reports success whether or not the model is right.
4 · Collect coverage, and see what moved

The same ELF is replayed on the coverage-instrumented model, and the testplan is regenerated from the trace. PMP coverage, measured before and after adding four more access kinds to the same region:

CorpusPMP spans coveredof reachable
The one lw test81226  35.8%
Five tests — lw, sw, lr, sc, amo85226  37.6%
Four extra spans for four extra tests is the useful result, not a disappointing one. It says the permission check distinguishes access kinds and little else in that region, so the way to move PMP coverage is to vary the address relationship and the configuration — which is exactly what the derived cases do, and why they are derived rather than written.

The generated assembly, the ELFs, the coverage traces and the before/after testplans for this example are all in the repository, under demo/pmp-lw-denied/.

Executing and validating a generated test

Each test is a RISC-V ELF that decides its own verdict, so no harness is required. It reports through an HTIF (host-target interface) write to tohost, the mechanism riscv-arch-test and Spike already expect. One output format and one runner, so the same ELF runs unmodified on Sail, an independent simulator, and RTL.

 Step
1Generate assembly
2Assemble and link with the RISC-V toolchain
3Produce the ELF
4Run the ELF on Sail
5Run the same ELF on Spike or another independent simulator
6Collect both results
7Compare the architectural state, or the trap result
8Record coverage and classify any failure
ConcernHow it is handled
Matching configurationsA mismatched ISA string is the most common cause of an apparent disagreement between simulators, which is why they all derive from one parsed configuration
Classifying a failureEvery failure is classified as a model issue, a framework issue, or a correctly reported result. A bare pass/fail count is not an acceptable output
The two runs have different jobs. Sail is the Golden Model and provides the instrumented coverage. Spike, QEMU and RTL are independent environments, not derived from Sail, used for cross-platform validation.

Coverage does not depend on the two agreeing. A disagreement is classified and reported, and the Sail run still contributes its coverage — coverage is a property of what the model executed.

Coverage, and what 100% means

The RFP asks for coverage in terms of the Sail code, so it is measured from the instrumented model. For each configuration the framework first determines which targets are reachable; those are the denominator. A target is covered when at least one test reaches it.

100% coverage means that every reachable, in-scope Sail coverage target for a selected configuration is exercised by at least one generated test.

Reachable denominator = instrumented targets minus configuration-infeasible, structurally unreachable, and explicitly excluded targets.
Excluded from the denominatorExampleEvidence
Structurally unreachableinternal_error arms; the reverse direction of a bidirectional mappingReaching it would mean the model is broken, or that a decode path exists which does not
Proved unreachableA path for which the solver returns UNSATA proof from the symbolic backend
Configuration-infeasibleA target needing an extension this configuration does not enableThe configuration file. It is counted in a configuration that does enable it
Sail coverage and ACT4 coverage are different measures. Sail coverage measures model execution targets. ACT4 coverage and certification requirements are handled separately where applicable. Sail coverage is not equivalent to RISC-V architectural certification coverage, and this proposal does not claim it is.

Results are reported per configuration, never averaged. Where FP and Vector sit outside the committed scope, both the in-scope and combined figures are given, so the deferral neither flatters nor hides the result.

ACT4 integration

How does a generated test run through the RISC-V Architectural Certification Test (ACT4) framework? We produce the test in ACT4’s own format; its existing pipeline does the rest unchanged.

What the project delivers for ACT4
ACT4-compatible generated tests
The test metadata and configuration header ACT4’s discovery reads
Build integration: tests build under ACT4’s own make
Simulator execution through ACT4’s runner
Pass/fail reporting, and the signature region where one is requested
CI integration, as committed in Deliverable 4
This is integration, not certification. The project delivers integration with the ACT4 framework. It does not deliver architectural certification, and no claim of compliance is made on the basis of this integration. Coverpoint tagging is a stretch item and is listed as such.

ACT4 integration points

The requirements a generated test must satisfy to build and run under ACT4’s own pipeline. All are implemented.

Integration pointRequirement
Compile configurationThe framework’s Sail compile configuration is cross-checked against ACT4’s own, so both describe the same machine
Host interface symbolstohost/fromhost must be a real, sized, backed section. A host interface reads the symbol’s ELF size and will not start if it is zero, which a bare label gives
Signature regionbegin_signature/end_signature must bracket real data, because ACT4 extracts results between those symbols
Test-config headerACT4’s test discovery reads it. Zicsr is declared unconditionally, because the preamble always writes the trap vector whatever the tested instruction needs
Section placementThe .text.init section name matches the address ACT4’s linker scripts fix, which is also the generator’s own default, so a test lands correctly under either script
