Part 2

What Sail is, and what it produces

Sail is a language for writing down what an instruction set architecture does. Not a prose specification and not an implementation — an executable definition. The RISC-V Sail model is the architecture written in it, and RISC-V International has adopted it as the Golden Model: the authority on what the ISA means.

1. What is its purpose?

To have one definition of the architecture that can be executed, reasoned about, and checked, instead of a document that humans interpret differently. An instruction is defined once:

function clause execute (ITYPE(imm, rs1, rd, op)) = {
  let rs1_val = X(rs1);
  let immext : xlenbits = sign_extend(imm);
  let result : xlenbits = match op {
    RISCV_ADDI  => rs1_val + immext,
    RISCV_SLTI  => zero_extend(bool_to_bits(rs1_val <_s immext)),
    ...
  };
  X(rd) = result;
  RETIRE_SUCCESS
}

That definition is simultaneously the specification, the simulator, and — for this project — the source of the tests.

2. What is it used to generate?
OutputProduced byUsed here for
A C emulatorsail -c → sail_riscv_simRunning generated tests, and acting as the oracle that supplies expected results
An Isla IR fileisla-sail → riscv64.irSymbolic execution — solving for inputs that reach a chosen branch
A coverage manifest-DCOVERAGE=ON → .branch_infoThe denominator: every instrumented span the model contains
Documentation, SMT theories, theorem-prover definitionsother Sail backendsNot used by this project, but the same source serves them
3. How does it compile?

Sail is a compiler with several back ends. Two matter here.

StepWhat happensWhy it matters to us
Parse and type-checkSail's type system is dependent on values — a bitvector's width is part of its typeThis is why illegal-width code cannot be written, and why VLEN has to be fixed at compile time
Lower to JIBAn imperative intermediate representation: no pattern matching, no polymorphism, explicit control flowJIB is what both back ends consume
C back endJIB → C → sail_riscv_simThe executable Golden Model. With -DCOVERAGE=ON it also records which spans ran
isla-sail back endJIB serialised to a .ir text file rather than compiled to CLets isla interpret the model with symbolic values instead of concrete ones
Two compile-time facts shape the whole design. First, isla-sail is a Sail plugin: it links libsail and registers itself as a target, so it tracks the same front end as the C build rather than reimplementing it. Second, --isla-preserve is mandatory on the entry points — without it they are pruned as dead code and the IR decodes nothing, with no error message. Configuration is baked in at this point too: type vlenbits = bits(vlen) monomorphises, so XLEN and VLEN are frozen in the IR, not chosen at run time.
4. How does Sail support test generation?
Property of SailWhat it enables
The model is executableIt can be the oracle. Run an instruction, read the resulting state, and that state is the expected answer — nothing has to be derived by hand
The model is declarative about encodingsmapping clause encdec gives the bit pattern of every instruction. The generator reads the instruction set from the model rather than from a separate list, so a new instruction is picked up automatically
The model is symbolically interpretableVia the IR, the conditions a branch imposes can be extracted and solved, instead of guessed at
The model is instrumentableSail can emit a span manifest and a run-time trace, giving branch coverage against the specification itself — which is exactly the coverage measure the RFP asks for
The model declares its own configurationMemory map, PMP entry count, grain, enabled extensions. Test setup reads these instead of assuming them
The consequence for maintenance. Every one of those five is a link back to the model rather than a copy of it. When the architecture changes, the instruction list, the encodings, the expected results and the coverage denominator all move with it. No table in this framework needs hand-editing when an instruction is added — which is the strongest answer we can give to the RFP's long-term-maintainability criterion.

Prior Sail-based test-generation approaches

The RISC-V Sail ecosystem has supported more than one style of test generation, and the distinction between them is the foundation of what we propose.

 The REMS generator — earlierIsla — later
What it does Uses Sail-derived instruction information to produce random instruction streams: choose instructions and operands, generate executable tests, and use the Sail model as the reference for expected behaviour Executes Sail symbolically and uses an SMT solver to determine values that reach specific feasible paths through the model
PurposeBroad instruction-level testingSpecification coverage — automated instruction-sequence generation aimed at reaching named behaviours
Model snapshotGenerated from Sail's OCaml generator backendSerialised JIB IR, tracking the current Sail front end
Track recordPublished as a randomized RISC-V instruction generator based on the Sail modelMorello — model-based tests checking consistency between the Sail specification and implementations, also used in Morello QEMU development
These are complementary, not competing. The concrete approach is inexpensive and can exercise functionality symbolic execution cannot easily represent. The symbolic approach earns its keep when choosing values at random is unlikely to reach an interesting model behaviour. The REMS work is the prior art for concrete and random generation; our contribution is turning concrete Sail execution into one backend inside a broader, model-derived, configuration-aware, privileged-architecture framework — not replacing it.

isla-testgen, and how it uses Sail

isla is a symbolic execution engine for Sail specifications, from the same research group that produced Sail. isla-testgen is the test generator built on it, used most notably for Morello, where model-based tests checked consistency between the Sail specification and real implementations and were carried into Morello QEMU development. Both are existing open-source work; we added a RISC-V target rather than starting over.

The idea is short: run the model with unknowns in place of register and immediate values. Every branch the model takes adds a condition on those unknowns. At the end you hold a list of conditions — a path condition — and you hand it to an SMT solver, which either produces values that satisfy it or proves that none exist.

From IR to assembly to ELF

Solving gives numbers. Turning numbers into a runnable, self-checking program is a separate job, done by the target's own object emitter.

StepWhat is producedDetail
1Concrete pre- and post-stateextract_state.rs asks the solver for a model and reads out every register and memory region as a fixed value. Nothing symbolic survives this step
2A .s assembly filegenerate_object_riscv.rs writes: the preamble that builds machine state, the instruction under test as raw bytes, tables of expected values, a trap handler, and the pass/fail reporting code
3A .ld linker scriptEvery section pinned at a fixed, non-overlapping address, with ENTRY(preamble)
4An .elfThe real GNU assembler and linker are invoked — no bespoke ELF writer
Why raw bytes rather than mnemonics. The test must exercise the exact encoding the model decoded, not whatever an assembler decides a mnemonic means. It also lets the generator emit encodings no assembler will accept, which is how illegal-instruction behaviour gets tested at all.
Why the tests check themselves. The expected values are compiled into the ELF as data, and the program compares against them and reports through an HTIF tohost write — the mechanism Spike already expects. So a test is a plain ELF that any simulator can run with no harness, no wrapper and no host-side script, and it decides its own verdict. That is what makes the same artefact portable across Sail, Spike, QEMU and RTL.

What isla-testgen is good at, and what it cannot do

Both lists come from building on it, not from reading about it. The limitations are the reason this proposal is for a hybrid rather than for scaling one engine up.

StrengthWhy it matters
It reaches branches on purposeName a branch, get a test that executes it — or a proof that nothing can. Random generation reaches deep conditions only by luck
It proves unreachabilityUNSAT converts a permanent coverage gap into a justified exclusion. Without this, 100% is unattainable and the remaining percent is unexplained
It knows the exact final stateThe post-state comes from the same solve, so the test asserts a complete answer rather than a hash or a signature
It handles rare and awkward inputs naturallyDivide-by-zero, misaligned addresses, boundary values — these are just constraints, not special cases someone had to think of
It tracks the model automaticallyThe instruction set and its encodings are read from the .sail sources
LimitationWhat actually happensConsequence
Floating pointThe model declares riscv_f32Add and friends as vals with no body — SoftFloat is external C. Symbolically they are holesWe wrote a 431-line symbolic SoftFloat interface, and FP arithmetic is still routed to the oracle in practice
Vector, at realistic VLENisla's widest bitvector is 129 bits. VLEN 256 and 512 cannot be represented at allVector goes to the oracle. This is a hard structural bound, not a performance issue
Machine stateThe solver derives instruction operands. It has no notion of "put a PMP entry here" — nothing in the model asks for thatMachine state is constructed arithmetically in the preamble. This is a design boundary, not a defect — see the control layer
Control transfers into solved codePlacing an opcode at an address reached through a data-computed jump is unsatisfiablePrivilege changes and page-table installs must happen in the preamble, before isla's region
Path explosion on deep functionsA full Sv57 walk multiplies paths per levelManageable in practice, but depth is the cost model to watch
Cost per testEvery test is an SMT solveFine for targeted work, wrong tool for bulk volume across a 16-configuration matrix
The honest summary. isla-testgen is a precision instrument. It is the right tool when you know which branch you want and need to be sure you reached it, and the wrong tool when you need many tests, wide configurations, or any part of the model it cannot represent. Both halves of that sentence are load-bearing for the design that follows.

The REMS random-generation lineage

The same research programme that produced Sail and isla — REMS, Rigorous Engineering of Mainstream Systems — also established the other approach to generating tests from an executable model, and it is much older and simpler: use the model as an oracle.

How it generates a test
StepWhat happens
1Pick an instruction and fill its operand fields — randomly, or from a constrained generator that knows which fields are legal
2Build a small program that sets up registers, executes it, and stops
3Run it on the model. Whatever state comes out is, by definition, the correct answer
4Emit the same program again with that state written in as assertions
5Run the result anywhere. Any implementation that disagrees with the model fails

No solver, no reasoning about the model's internals — only execution. The RFP cites this lineage directly, and the CHERIoT work in isla-testgen itself follows it.

The REMS OCaml random generator for RISC-V exists but is not usable as a base. Its last commit is 2019 and it is pinned to a Sail AST shape seven years stale. We took the method and rebuilt it against the current model rather than reviving the code — which is also why our instruction list comes from parsing the model rather than from that generator's tables.
Symbolic (isla-testgen)Model-as-oracle (REMS lineage)
Question it answersWhat inputs reach this branch?What does the model do with these inputs?
Needs the model to be…symbolically interpretablerunnable
Cost per testAn SMT solveOne simulator run
Reaches deep conditionsBy constructionBy luck
Proves unreachabilityYesNo
Handles FP and wide vectorsNoYes — it is just execution
Scales to many configurationsPoorlyWell
Every row is a mirror image. Each method's weakness is the other's strength, with no overlap in the failure modes. That is unusually clean, and it is the whole argument for combining them rather than picking one.

The concrete oracle, and how it complements isla

Our oracle (autotest/, package sailtest) is the REMS method rebuilt against the current model, with two deliberate departures.

DepartureWhat we doWhy
Not random — enumeratedThe instruction list and its encodings are parsed from the .sail sources, then swept systematicallyRandom sampling cannot tell you what it missed. Enumeration gives a denominator, and picks up a new instruction the day it is added to the model
Two ELFs, one bodyA probe ELF runs first and prints the result registers; the final ELF is the same program with those values compiled in as assertionsThe expected state is observed, never predicted, so nothing has to model the instruction a second time
The circularity we state openly. Expected values come from sail_riscv_sim, so re-running an oracle test on Sail proves only self-consistency. The independent evidence comes from running the same ELF on Spike, QEMU or RTL. Any figure we publish says which simulator produced it.

What is enhanced in our concrete-generation approach

Concrete Sail execution is established prior art, notably in the REMS RISC-V instruction generator. This framework retains that approach as a concrete backend and adds four things.

AdditionWhat it changes
Model-derived inventoryThe instruction list and configuration come from the current Sail model, not from a 2019 snapshot generated by Sail's OCaml backend. A new instruction is picked up the day it is added
Explicit privileged-state constructionA preamble builder that constructs PMP entries, page tables, privilege transitions and interrupt conditions — the reason privileged targets are reachable at all
Fail-capable test gatingA test is rejected unless it has an observable expected result, and a negative control where one applies. A suite that cannot fail is not evidence
Independent differential validationEvery ELF runs on Sail and an independent simulator, so the Sail result is never the only evidence about itself
Combined with symbolic generation for targets that concrete selection is unlikely to reach, the result is a single framework in which the oracle serves as both a directed and a random generator, rather than a random generator standing alone.

ISLA testgen versus oracle testgen

The routing rule is not a preference. It follows from what each method can represent.

CaseWhich route, and why
Signed overflow on a divide Symbolic. A concrete generator is unlikely ever to choose the exact operands for a rare case such as INT_MIN / -1. Symbolic execution derives them from the path condition — it is not searching, it is solving
Floating point Concrete. The Isla work has explicit limitations here; the model's SoftFloat operations have no symbolic body to execute
Wide vector state Concrete. A representation limit, not a difficulty — isla's widest bitvector cannot hold VLEN 256 or 512
A named privileged branch Symbolic. Reaching it by random choice is chance; reaching it by solving is construction — and UNSAT proves when it cannot be reached at all
Bulk coverage across a configuration matrix Concrete. One simulator run per test, against an SMT solve per test
The Isla research itself notes scalability and representation limits when applying symbolic execution to full ISA semantics. We treat that as a design input rather than an obstacle: it is precisely why a concrete route remains necessary, and why the routing decision belongs in the control layer rather than in a person's judgement per test.
Part 3

The proposed framework

The framework combines the two complementary approaches under a common configuration, validation and coverage flow. It is a configuration-driven, coverage-guided loop built around the Sail RISC-V Golden Model.

 StageWhat happens
1Resolve and enumerate For each configuration, resolve the model configuration and build a reachable target list, including an explicit record of the targets that configuration excludes
2Classify and route ISLA + Z3 where symbolic constraint solving can derive operands, paths or privileged machine state. The concrete oracle where direct execution is more appropriate, including floating-point and vector functionality. Templates as a limited backstop for branch and jump cases
3Build the state A common preamble builder establishes the required privileged architectural state before the test executes — shared by both routes
4Gate on quality Each test is emitted as a standalone RISC-V ELF and must pass a gate requiring an observable expected result and, where applicable, a negative control
5Execute and differentiate The same ELF runs on the instrumented Sail model and on an independent simulator. Comparing the two is what separates model behaviour from a simulator or framework issue
6Measure and re-route Reachable-target coverage, Sail source coverage, self-checks and cross-platform checks are reported separately. Uncovered targets are classified and routed back to the appropriate generator, and the configuration is regenerated until its reachable targets are covered
Each configuration keeps its own denominator. The process repeats for every committed Golden Model extension across configurations, and each retains its own reachable target count, exclusions, coverage results and evidence — rather than being combined into a single headline figure. A number that averages sixteen configurations tells a reviewer nothing about any of them.

How the control layer operates

It is the component that turns "we have two generators" into "we have a method". Four jobs.

 JobWhat it decides, and on what evidence
1ConfigureReads one Golden Model configuration and derives everything downstream from it — the IR to load, the assembler's -march, the simulator's ISA string, which extensions exist. Previously re-derived in four places, which is how they drifted apart
2RouteSends each target to the generator that can reach it. FP arithmetic and wide vectors to the oracle because isla cannot represent them; named privileged branches to isla because random execution reaches them only by luck. The routing table is evidence-backed per extension, not a guess
3Execute and judgeRuns each ELF on the Golden Model and on at least one independent simulator, and classifies every failure as model fault, framework fault, or correctly routed. A bare pass/fail count is not an acceptable output
4Measure and re-planReplays the corpus against the instrumented model, reconciles every span to hit / missed / excluded-with-reason, and turns the remainder into a stimulus queue that names what is missing rather than only where
One rule the control layer enforces above all others: architectural state is built in the preamble, never solved for. The solver derives instruction operands; PMP entries, page tables and privilege transitions are constructed arithmetically before the test region begins. Attempting the reverse fails outright — isla cannot place an opcode at an address reached through a data-computed control transfer. This single boundary is what made every privileged scenario in the framework possible.

Five things the derivation found that hand-writing had not

An aligned access cannot straddle an aligned bound Region bounds are pmpaddr × 4, so reaching PMP_PartialMatch needs an NA4 or TOR region at a 4-aligned but not 8-aligned bound, with an 8-byte access. That span had never been executed

A denied prefetch raises nothing The model returns a nominal exception internally so the calling instruction can decide not to prefetch. Expecting a trap is wrong, and the arm still needs a case

The coverage flow

The RFP asks for coverage in terms of the Sail code. That is what this measures — not instruction counts, not a functional coverage model we invented, but branches in the specification's own source.

How the branch trace becomes a number
StepWhat happens
1Build the model a second time with -DCOVERAGE=ON. Sail instruments each span and emits sail_riscv_model.branch_info — the complete list, with kind and exact source position
2Run an ELF with SAILCOV set. The emulator appends one line per executed span to sail_coverage
3Replay the whole corpus and take the union of executed spans. Per-ELF sets are also recorded, which is what lets a single test's contribution be measured
4Subtract the exclusion list. Sail's bidirectional mappings generate reverse directions that instruction execution can never take; internal_error arms are unreachable by construction; some spans need an extension the configuration does not have
5Report against a declared scope. The RFP's current deliverable excludes FP and vector, so both numbers are always published — in-scope and combined — because each alone flatters or hides
A percentage is only as good as the run behind it. Span totals from the manifest are stable; percentages depend on which corpus was replayed, and a partial replay is easy to mistake for a full one. Every figure that leaves this project names its corpus and its date.

Running on Sail and Spike

Nothing special is required, and that is the point. A generated test is a plain ELF that decides its own verdict, so running it is one command per simulator.

sail_riscv_sim  --config <cfg.json>  test.elf
spike           --isa=rv64imac_zicsr  test.elf
ConcernHow it is handled
How does a test report?An HTIF write to tohost: a nonzero odd value halts the simulator, pass and fail encoded exactly as riscv-arch-test's own RVMODEL_HALT_PASS/FAIL
Why not an ecall?Tried first, and wrong: that is the syscall-proxy convention, only active under spike pk. On a bare-metal ELF the ecall traps back into our own handler instead of halting
Matching configurationsThe ISA string, the -march and the model's config all derive from one parsed configuration. A mismatch here is the most common cause of a spurious "Sail and Spike disagree"
Which result is evidence?For oracle tests the Sail run is self-consistency only. Spike, QEMU and RTL are the independent checks. Reports label which is which
Beyond the twoQEMU and CVA6 RTL already run the same artefacts unchanged, which is the practical demonstration that the ELFs are portable

Where the PMP cases come from

Not from a hand-written list. The deciding function is read, and the cases are the distinctions it can actually make. The register state is 24608 configurations; pmpCheck distinguishes about 44, because it composes three stages that read disjoint state, so the counts add rather than multiply.

StageReadsCases
Address matchthe address and pmpaddr17
Permission checkthe access kind and R/W/X18
Privilege overrideprivilege and the lock bit4
Structuralentry 0, priority, fall-through, zero entries5
Total 44, not 1,224
The address range collapses to five positions, and this is provable rather than conventional. pmpRangeMatch compares only addr and addr + width against the two region edges, so every address in 264 is either below, straddling the low edge, inside, straddling the high edge, or above. The two straddling cases fault regardless of permissions and are the ones hand-written suites omit.
One case the branch structure cannot see. NAPOT computes its bounds with mask arithmetic. A bug there produces wrong bounds without changing any branch — so several region sizes are tested anyway, with that reason recorded. The rule is coverage-guided where branches exist, value-guided where the code is arithmetic.

Trap handlers

Every generated test carries one. It is emitted as assembly by the object writer, not linked in from a library, so it can be specialised per test.

BehaviourHow it is produced
Default: any trap fails the testmtvec is armed by the preamble's first instruction, and the handler jumps straight to the failure path
Expect a specific cause--expect-trap-cause <n>: read mcause, compare, and continue only on an exact match
The trap is the result--trap-is-pass: report success from inside the handler. Required for any violation test — a faulting instruction never wrote its destination register, so resuming into the normal comparison fails by construction
Resume correctly after a trapAdvance mepc by 2 or 4 bytes depending on whether the trapping instruction was compressed. riscv-arch-test's own handler had a fixed advance until this was fixed there; ported rather than re-discovered
Delegated trapsRead scause, not mcause. Reading the wrong one is exactly how a delegation test passes without delegation having happened
The guard that stops a false pass. Because mtvec is armed first, every later preamble step — enabling FP, programming PMP, building a page table — runs with the handler live. A fault raised there carrying the expected cause would report success having never reached the instruction under test. The handler therefore also checks that mepc is at or beyond test_start. Negative controls do not catch this, because they vary the expected cause rather than the trap's origin.

Interrupts and exceptions

Exceptions are synchronous and come from the instruction under test. Interrupts are asynchronous and have to be arranged, which takes three separate conditions — and getting one wrong produces a test that looks like it passed.

FlagWhat it arrangesWhat it tests
--pending-interruptPending (via the memory-mapped CLINT, since mip.MSIP is read-only to CSR writes) and enabled in mie, but mstatus.MIE left clearwfi — it must resume on a pending enabled interrupt without taking the trap
--deliver-interruptThe same, plus mstatus.MIE setActual delivery — the trap is taken
--delegate-interruptA supervisor software interrupt with mideleg set and stvec installedThat a delegated interrupt lands in S-mode instead of M-mode
Two traps that were found the hard way. Machine-level interrupts cannot be delegated — the model hardwires MEI/MTI/MSI in mideleg to zero, so setting mideleg.MSI writes 0 and the interrupt is still taken in M-mode, which reads as a delegation failure and is really an impossible test. SSIP is CSR-writable, so the supervisor variant needs no CLINT access. And an interrupt cause is the cause code with the top bit set, so a bare comparison against 3 can never match — the handler tests that bit as a sign bit, which keeps it XLEN-independent and stops an exception with the same low bits satisfying the test by accident.

Translation schemes

The model supports Sv32, Sv39, Sv48 and Sv57, with a dependency chain the configuration validates. Which one is active is decided in the preamble, by what is written to satp.

DecisionWhere it is made
Bare, or translatedsatp.MODE. Note that translationMode opens with if priv == Machine then Bare — M-mode never translates, so every VM test must first drop to Supervisor
Which schemeThe MODE field — 8 is Sv39. The generator emits Sv39 today; Sv32, Sv48 and Sv57 are planned work in Milestone 3
The page table itselfEmitted into .data by the object writer: 512 entries, leaf PTEs at the root level, so each maps a 1 GiB gigapage and no second-level tables are needed at all
What is reachableTwo of 512 entries are mapped — the ROM/CLINT gigabyte and the code/data gigabyte. Leaving the other 509 invalid is what makes an unmapped-page test possible with no extra machinery
Identity-mapped on purpose. Every virtual address translates to the same physical address, so translation is genuinely active while every address the test already uses stays valid. And sfence.vma follows the satp write, because an implementation is free to have cached translations from before it changed.

Virtual memory protection

Permissions are decided by check_PTE_permission, which is three gates in sequence — steps 6, 7 and 8 of the architecture's translation algorithm — each reading a different part of the machine.

GateReadsThe case that is easy to miss
6pte.U, privilege, mstatus.SUMSUM lets Supervisor touch a User page for loads and stores but never a fetch — one guard, and a whole class of test
7The R=0 W=1 X=0 shadow-stack encodingIt returns rather than falling through. Step 8 asks for pte_W & pte_R on an atomic, which would re-deny the very access the encoding exists for
8R/W/X, after mstatus.MXR rewrites pte_RMXR makes an execute-only page readable with no PTE changing at all
Page tables are not the whole state. MXR, SUM and MPRV each change the answer without touching a PTE. A plan that varies only page tables tests a fraction of the space.
Virtual memory cannot be tested apart from PMP, and the coupling is structural. Dropping to Supervisor to enable translation simultaneously arms PMP's default-deny, so every VM test carries a PMP configuration whether or not PMP is the subject. And the walker's own PTE reads are themselves PMP-checked. That yields the single most valuable joint test: use PMP to deny the region the page table itself lives in. A correct implementation reports an access fault; a wrong one reports a page fault. Neither feature alone can reach it.

The same derivation applies as for PMP. pte_is_invalid is eight independent disjuncts, four of which are only reachable with an extension turned off — so they are configuration-dependent targets, which is one concrete reason the configuration matrix matters for coverage and not only for compatibility.

Definition of complete

Completion is measured by coverage of the reachable targets in the Sail model's branch structure. The ideal is 100% for every extension and operating mode in scope.

The word doing the work there is reachable. A raw percentage against every instrumented span is not achievable and not meaningful, because the denominator contains code no test can execute. Three kinds, each excluded with a written reason rather than quietly dropped:

ExclusionExampleEvidence for the exclusion
Unreachable by constructioninternal_error arms — a malformed access the decoder cannot produceThe arm exists to catch a bug in the model itself; reaching it would mean the model is broken
Proved unreachableA path the solver returns UNSAT forA proof, from --all-paths-for. This is the strongest form and is unique to the symbolic route
Not in this configurationA span needing an extension the build does not enableThe configuration file. It becomes reachable in a configuration that enables it, and is counted there
Two figures are always published, never one. Excluding floating point and vector raises the percentage, because they are the better-covered half. Quoting only the in-scope figure flatters the work; quoting only the combined figure hides that the actual deliverable is the less complete half. Both appear, with the scope file that justifies the split.
