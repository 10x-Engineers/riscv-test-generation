PMP Coverage Walkthrough

One lw against a PMP region with no read permission — generated, run, measured, planned against, and then regenerated to close the gap the plan found. Every number below came from a command run today.

Step 1

Generate the test

One command. The instruction is a plain lw; the PMP configuration is a flag.

isla-testgen -A riscv-ir/riscv64.ir -C riscv-ir/riscv64.toml -a riscv64 \
  --memory-region 0x80020000-0x80030000 -o lw_pmp_read_denied -n 1 \
  0x80020137 0x02011113 0x02015113 0x00012083 \
  --pmp-deny 0x80020000 --expect-trap-cause 5 --trap-is-pass
PartWhat it is
0x80020137 0x02011113 0x02015113lui / slli / srli — put 0x80020000 in x2
0x00012083lw x1, 0(x2) — the instruction under test
--pmp-deny 0x80020000Entry 0 denies all access to the 4 KiB region there; entry 1 permits everything else
--expect-trap-cause 5Load access fault — from accessFaultFromAccessType, Load(Data) => E_Load_Access_Fault()
--trap-is-passTaking that trap is the result. Without it the harness resumes into a comparison that fails by construction

What the generator emitted

/* PMP entry 0: deny *all* access to the 4KiB region at 0x80020000;
   entry 1: permit everything else. PMP is first-match, so the
   denying entry has to be entry 0 — reversed, the catch-all matches
   first, nothing is ever denied, and the test would pass while
   proving the opposite of what it claims. */
li   x31, 0x200081ff          (0x80020000 >> 2) | 0x1ff — 4 KiB NAPOT
csrw pmpaddr0, x31
li   x31, -1
csrw pmpaddr1, x31
li   x31, 0x1f98              [0]=L|NAPOT|no perms, [1]=NAPOT|RWX
csrw pmpcfg0, x31

And the handler that decides the verdict:

trap_vector:
  csrr x30, mcause
  li   x31, 5
  bne  x30, x31, comparison_fail   wrong cause → fail
  csrr x30, mepc
  la   x31, test_start
  bltu x30, x31, comparison_fail   trap came from the preamble → fail
  li   t5, 1
  j    write_tohost                the trap IS the pass
That second check is the one people miss. mtvec is armed by the preamble's first instruction, so a fault raised while programming PMP would carry cause 5 too and report success having never reached the lw. Right cause, entirely wrong reason.
Step 2

Run it — and prove the pass is real

TestSail Golden ModelSpike (independent)Expected
lw_pmp_read_deniedSUCCESSpasspass
NEG_wrong_addressFAILUREFAILmust fail

A passing test proves nothing on its own. The first control denies a region the test never touches — if it still passed, the fault was coming from somewhere else. The second expects cause 7 instead of 5 — if it still passed, the handler was noticing a trap rather than the trap. Both fail, so the pass means what it says.
Step 3

Measure the coverage

SAILCOV=1 build-coverage/c_emulator/sail_riscv_sim --config rv64.json lw_pmp_read_denied.elf

That appends every executed span to sail_coverage — 2,162 lines from this one test. Reconciled against the model's own span manifest:

One test reaches a third of the PMP enforcement code. That is not because the test is clever — it is because a denied access runs the whole decision path: address match, permission check, privilege override, fault construction.

Step 4

What the testplan says to do next

testplan.py enumerates the model's whole span manifest as plan items, then joins coverage in as a status column. The plan does not shrink when tests are added — it fills in.

14,975 spans → 2,347 plan items (2,347 reachable, 0 held unreachable)

state           items
not started      1934
partial           198
complete          155
out of reach       60
pmpCheck was listed out of reach. That is the plan telling us something specific: with only this one test, the item cannot be completed — not that it is impossible, but that no stimulus in the corpus can finish it. That is the line that drove step 5.
Step 5

Regenerate against the gap

pmp_regs.sail did not move at all, and that is the finding. Four new tests, four more enforcement branches, and zero progress on the register file — which is two thirds of the PMP code. Enforcement tests exercise pmp_control.sail; nothing here writes a pmpcfg value and reads it back to check what the model kept. That is a different campaign, and it is the larger one.

The loop

What this demonstrates

 StageOutput
1GenerateA self-checking ELF from the unmodified model, with the PMP state built in the preamble
2RunPasses on Sail and Spike; both negative controls fail, so the pass is meaningful
3MeasureBranch coverage against the Sail sources — 35.8% of pmp/ from one test
4PlanpmpCheck flagged out of reach, with the reason visible
5RegenerateFour tests aimed at the named arms
6Re-measure37.6%, 7 of 19 arms, pmpCheck complete — and a new gap exposed
Step 6 producing a new gap is the point, not a shortfall. The loop does not terminate in "done"; it terminates when every reachable span is hit or excluded with a written reason. Right now it is telling us the next campaign is CSR read-back on pmp_regs.sail — 149 spans, 28.9% covered, and not one enforcement test will move it.
