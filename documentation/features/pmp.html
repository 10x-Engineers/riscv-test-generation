PMP, End to End

How the PMP case space is derived from the model rather than curated, what one generated test actually reaches, and what it takes to stop choosing the configurations by hand.

The case space is derived, not chosen

PMP's architectural state is pmpcfg_n (512 bits) plus pmpaddr_n (4,096 bits) — 24608 configurations. It cannot be enumerated, sampled or fuzzed. But pmpCheck does not distinguish 24608 cases; it distinguishes about 44, because it composes three stages that read disjoint state, so the counts add rather than multiply.

One case no branch can see. NAPOT computes its bounds with mask arithmetic, so a bug there gives wrong bounds without changing any branch. Several region sizes are tested anyway, with that reason recorded: coverage-guided where branches exist, value-guided where the code is arithmetic.

The access side, and what it costs

pmpCheckRWX has 19 arms. Three are internal_error — unreachable by construction, recorded as exclusions. The prefetch arm expands to three leaves, so there are 18 distinct permission checks across five patterns: R, W, X, R&W (atomics and shadow stack) and R|W (cache management — the only disjunction).

Both negative controls — wrong cause, and denying a region the test never touches — fail as required, so the passes mean what they say.

pmp_regs.sail did not move by one span, and that is the finding. Two thirds of the instrumented PMP code is register semantics — WARL legalisation, grain, lock behaviour — and no enforcement test will ever touch it. Nothing yet writes a pmpcfg and reads it back to check what the model kept. That is the larger, less covered half, and it needs a different kind of test.

The methodology: two steps

Today the configuration is a flag — --pmp-deny <addr>, with the NAPOT encoding hardcoded in Rust — so TOR, NA4, read-only, unlocked and priority cases would each need a new flag. The proposed method removes the human from both halves:

Step 1  derive the case space from the model   →  pmp_cases.json
         one row per case: pmpaddr, pmpcfg, access address, expected outcome

Step 2  cross each case with the memory operations the
         instruction sweep already solves            →  one ELF per pair
StepWhat it does, and what it must get right
1 — casesModes from enum pmpAddrMatchType, fields from bitfield Pmpcfg_ent, positions from pmpRangeMatch, legality bounds from memory.pmp. It must emit the address as well as the config: “inside the region” is a relation between the two, not a property of either
2 — crossOnly Match cases are worth crossing — NoMatch never reaches pmpCheckRWX and PartialMatch faults before it — which keeps this at tens of tests, not 17×18. And the expectation must be recomputed per access kind from pmpCheckRWX, not inherited: a config with R=1 W=0 permits a load and denies a store

The join is cheap because the access address arrives via lui/slli/ srli in the preamble, so pointing a solved memory operation at the case's address is arithmetic, not a re-solve. PMA takes the same shape, with one difference: pma_regions comes from config memory.regions, so its step 1 emits config JSON variants rather than preamble writes.

How step 1 gets built — three routes, two now ruled out

RouteResult
Static enumeration from the model Works, and is cheapest. testplan.py already names the deciding expression (match pmpAddrMatchType_encdec(ent[A])); expanding it into concrete cases is an extension to it, not a new tool
Write PMP via csrw in the opcode sequence Does not enumerate — measured. Unconstrained, killed at 12 GB: one csrw pmpcfg0 on RV64 runs pmpWriteCfg eight times, each forking. Masked to one entry it completes but yields one path, because isla-testgen solves instruction by instruction and the write concretises the value before the load can branch on it
Symbolic at init The route for the cases arithmetic alone cannot give. Make pmpcfg_n/pmpaddr_n symbolic after isla_testgen_init returns — the mechanism execution.rs already uses for the PC. Before init is pointless: reset_pmp() would zero them. Bound it to one entry, or the eight-fold legalisation explodes however the value arrives
What the solver buys that a table cannot. The write passes through pmpWriteCfg's WARL legalisation, so it physically cannot return a configuration the model would refuse — and it returns non-obvious legal ones. In the run above it chose W=1 R=0, the reserved encoding, which survives only because this configuration permits it. It also answers UNSAT, which is what turns an untested span into a justified exclusion rather than a gap.
