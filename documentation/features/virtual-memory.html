Virtual Memory, End to End

Sv39 address translation: the six files it lives in, how the preamble builds a page table, where permissions are actually decided, and why virtual memory cannot be tested apart from PMP.

First, two things people get wrong

Page tables are not the whole state, and this is not a separate feature from PMP

The assumptionWhat the model actually does
“The PTE bits decide the outcome” Three mstatus bits change the answer without touching a page table: MXR makes execute-only pages readable, SUM lets Supervisor read User pages, and MPRV changes which privilege the check even runs at. Identical page tables, different results
“Translation and PMP are separate campaigns” The walker's own PTE reads are physical accesses, and go through PMP. That is Load(PageTableEntry) — arms 3 and 7 of pmpCheckRWX. A PMP denial during a walk produces an access fault where every other failure produces a page fault, and that pair is only reachable with both features configured at once
“A test can run in M-mode like the others” translationMode opens with if priv == Machine then Bare. Machine mode does not translate at all. Every virtual-memory test must first drop to Supervisor, which is why --run-in-supervisor is not optional here
The ordering, which the model states directly. Translation runs first; PMP and PMA then run on the physical address it produced. A comment in update_PTE_Bits says so while explaining a different problem: “the PMA/PMP checks are done after address translation”. So a virtual address passes through two independent protection systems in sequence, and a test that configures only one of them is measuring half the path.
The shape of the problem

Six files, 588 spans — 2.6× the size of PMP

There is no vmem/ directory. The implementation is spread across five files in sys/ and one in core/, and it is the largest single feature in the privileged model.

FileWhat lives thereSpans

Worth knowing before scoping. PMP is 226 spans and the RFP lists it as required. Virtual memory is 588 and is listed as highly desirable. The larger feature is the optional one, so it needs a stated position in the plan rather than an implicit one.
Step 1

The foundation: three things the generator had to learn

Unlike PMP, nothing here was blocked by the symbolic engine. The obstacles were all about getting the machine into a state where translation is on.

CapabilityWhereWhy it was needed
Enter in Supervisor mode--run-in-supervisor M-mode translates nothing. The preamble sets mepc and mstatus.MPP and mrets into the test instead of jumping to it
Build a page table--sv39 There is nothing to walk otherwise. The preamble emits a real 512-entry root table into .data
Keep the harness alive--pmp-allow-all Below Machine mode, PMP denies every unmatched access — including the fetch of the test's own next instruction. Every VM scenario carries a PMP allow-all whether or not it is testing PMP
That third row is the coupling made concrete. There is no such thing as a pure virtual-memory test in this model. Dropping to Supervisor to enable translation simultaneously switches PMP from permissive to default-deny, so the PMP configuration becomes part of every VM test's setup whether you meant it to or not.
Step 2

Building the page table in the preamble

The generator emits an identity map — every virtual address translates to the same physical address — so that translation is genuinely active while every address the test already uses stays valid.

.data
.balign 4096                 a page table must be page-aligned; satp holds only its PPN
root_page_table:
  .dword 0x00000000000000cf  entry 0: VA 0x00000000 → PA 0x00000000, 1 GiB (ROM, CLINT)
  …
  .dword 0x00000000200000cf  entry 2: VA 0x80000000 → PA 0x80000000, 1 GiB (code + data)
  …                        the other 509 entries stay zero — V=0, invalid

Then it is installed and the TLB is flushed:

la    x31, root_page_table
srli  x31, x31, 12          satp holds the PPN, i.e. address >> 12
li    x30, 8
slli  x30, x30, 60          MODE = 8 = Sv39, in the top 4 bits
or    x31, x31, x30
csrw  satp, x31
sfence.vma                  an implementation may have cached the old satp

Four decisions in that table, and what each buys

DecisionReason
Leaf PTEs at the root level An Sv39 root entry covers 1 GiB. Making it a leaf gives a gigapage, so the whole identity map is one entry per gigabyte with no second-level tables to emit at all
Only two of 512 entries mapped Leaving the other 509 invalid is what makes an unmapped-page test possible. Pick any address outside those two gigabytes and the walk faults — no extra machinery needed
U stays clear (flags 0xcf = D|A|X|W|R|V) This is a Supervisor mapping. Setting U would make the page inaccessible to S-mode, not more permissive — the opposite of the intuition
D and A pre-set Avoids the A/D update path on every access. Clearing them is how that path gets tested deliberately — see Step 6
The shadow-stack alias is worth noting as a technique. Entry 1 optionally maps VA 0x40000000 to the same physical RAM as entry 2, but with flags 0xc5 = D|A|W|V — R=0 W=1 X=0, the reserved encoding Zicfiss defines as a shadow-stack page. It is an alias rather than a permission change on entry 2 because a shadow-stack page rejects normal loads and stores; converting the identity map would break every other test. The same physical memory is reachable two ways, and a test picks its view by which virtual address it uses.
Step 3

How the walk works

An Sv39 virtual address is not a number to be looked up — it is three 9-bit indices and a page offset, consumed one level at a time.

Step 4

Where permissions are actually decided

check_PTE_permission is the virtual-memory counterpart to pmpCheckRWX, and it is three gates in sequence — steps 6, 7 and 8 of the architecture's translation algorithm. Each reads a different part of the machine.

Step 6: privilege — and the asymmetry inside SUM

let priv_ok : bool = match priv {
  User       => pte_U,
  Supervisor => not(pte_U) | (do_sum & is_load_store(access)),
  Machine    => internal_error(…),   unreachable: M-mode never translates
};
mstatus.SUM lets Supervisor touch a User page — but only for loads and stores, never an instruction fetch. That single is_load_store guard is one branch, and reaching it needs a User page, S-mode, SUM set, and a fetch rather than a load. It is precisely the kind of case a hand-written testplan omits and a derived one finds by construction.

Step 8: the access table, after MXR

let pte_R = pte_R | (pte_X & mxr);      Make eXecutable Readable
match access {
  Load(_)             => pte_R,        Store(_)              => pte_W,
  LoadReserved(_)     => pte_R,        StoreConditional(_)   => pte_W,
  Atomic(_)           => pte_W & pte_R, InstructionFetch(_)  => pte_X,
  CacheAccess(CB_zero())    => pte_W,
  CacheAccess(CB_manage(_)) => pte_R | pte_W,
  CacheAccess(CB_prefetch(p)) => match p { PREFETCH_R => pte_R,
                                           PREFETCH_W => pte_W,
                                           PREFETCH_I => pte_X },
}

Structurally the same five permission patterns as PMP — R, W, X, R&W, R|W — but with one extra input PMP does not have: MXR rewrites pte_R before the table is consulted, so an execute-only page becomes readable without any PTE changing.

Step 5

The eight ways a PTE is invalid

pte_is_invalid is not one check. It is eight independent disjuncts, and each is a separate test case — reached before permissions are consulted at all.

#ConditionWhat it catchesNeeds
1V == 0An unmapped page — the ordinary case—
2R=0 W=1 X=0 & menvcfg.SSE == 0The shadow-stack encoding used without Zicfiss enabledconfig: SSE off
3R=0 W=1 X=1Reserved in all circumstances—
4non-leaf & (A|D|U set, or ext bits nonzero)A pointer PTE carrying leaf-only flags—
5N set & not SvnapotA NAPOT PTE on a machine without the extensionconfig: Svnapot off
6PBMT set & (PBMTE == 0 | bad encoding)Page-based memory type when it is not enabled, or encoding 3config or CSR
7RSW_60t59b set & not Svrsw60t59bSoftware-reserved bits without the extensionconfig: extension off
8reserved != 0Any other reserved bit set—
Four of the eight are only reachable with a specific configuration. Conditions 2, 5, 6 and 7 all test “this bit is set but the extension is off”. No page table alone can produce them — they need a build or a menvcfg write that turns the feature off. That makes them configuration-dependent targets, the same category as PMP's extension-gated access kinds, and it is why the 16-config CI matrix matters for coverage rather than just for compatibility.
Step 6

A read that writes: the A and D bits

After a successful walk, update_and_write_pte may write the PTE back — so a load can perform a hidden store, and that store is itself subject to PMP.

AccessSets D?Sets A?Why
InstructionFetch, Load, LoadReservednoyesRead-only accesses mark the page accessed, not dirty
Store, StoreConditional, AtomicyesyesThe ordinary write case
CacheAccess(CB_zero())yesyesThe spec has cbo.zero check and set both
CacheAccess(CB_manage(_))noyes“does not check the dirty bit and neither raises an exception nor sets the bit”
CacheAccess(CB_prefetch(_))nonoThe only access that touches neither
This is why the preamble pre-sets A and D. With both already set, update_PTE_Bits returns None() and no write happens — keeping every other test simple. Clearing them is how this path gets tested deliberately, and the pair Svade/Svadu decides whether the hardware performs the update or faults instead. Neither is exercised today.
One case the model flags against itself. A comment in update_PTE_Bits notes that for a failing sc.w the spec leaves it UNSPECIFIED whether the D bit is set, and the model chooses to set it because the PMP and PMA checks happen later and it cannot yet know the outcome. That is a deliberate, documented choice — a test asserting the other behaviour would be wrong, and it belongs in the exclusion list with that reasoning attached.
Step 7

Access fault or page fault: the distinction that catches real bugs

translationException has roughly thirty arms, but the entire structure is one question asked over every access kind:

FailureBecomesCauseReachable only by
PTW_No_AccessAccess Fault1, 5, 7PMP denying the walker's own PTE read
everything elsePage Fault12, 13, 15Invalid PTE, no permission, misaligned superpage

The access kind then selects which of the pair: load, store/AMO, or fetch. Shadow-stack accesses are deliberately reported as stores, even the ones that only read.

Getting this pair backwards is a classic implementation bug, and it is only reachable with both features configured. The test is: build a valid page table, then use PMP to deny the region the page table itself lives in. A correct implementation reports cause 5 or 7; a wrong one reports 13. No amount of page-table variation finds it, and no amount of PMP variation finds it — it needs both, which is the concrete payoff of treating them as one campaign.
Step 8

The TLB, and why it makes results order-dependent

The model caches translations in a 64-entry TLB. That means the same access can take two entirely different paths depending on whether it ran before — the first time it walks, the second time it hits.

ElementDetailTest consequence
Size26 = 64 entries, hashed on the VPNEviction is reachable, but needs 65 distinct pages
ASID matchingAn entry matches on ASID unless its global bit is setTwo satp values with different ASIDs must not see each other's entries
Global bitAccumulated down the walk — any level setting G makes the result globalA G bit on a non-leaf PTE still propagates; easy to implement wrongly
sfence.vmaFlushes by ASID, by address, by both, or everythingFour distinct flush behaviours, each its own branch
Nothing here is tested today. The preamble issues one sfence.vma after writing satp and never revisits the TLB. All 48 spans in vmem_tlb.sail are reachable only by a test that translates the same address twice, or changes satp mid-test — neither of which the generator can currently express.
Step 9

Executing and checking: what exists today

Five scenarios, three positive and two negative controls.

ScenarioFlagsExpectation
m3_supervisor_bare--run-in-supervisor --pmp-allow-allLoad succeeds with translation off — the baseline
m3_sv39_mapped… --sv39Same load succeeds through a real walk
m3_sv39_page_fault… --sv39, unmapped addressCause 13, load page fault; the trap is the result
m3_NEG_no_translationsame, but without --sv39Must fail. Cause 13 needs a real walk; without translation the same access faults differently
m3_NEG_mapped_address--sv39, but a mapped addressMust fail. A mapped address does not fault at all
The two controls do specific work. A page-fault test that passes proves nothing on its own — a test that traps for the wrong reason, or one where --sv39 silently did not take effect, looks identical to a correct pass. The first control proves the fault came from translation; the second proves it came from this address being unmapped rather than from something incidental.
Step 10

What the 588 spans say is missing

Three positive scenarios against the largest feature in the privileged model. The gaps are not subtle, and they rank cleanly by cost.

 GapWhat it needsCost
1Only lw is ever translatedVary the access: store, AMO, fetch. Step 8's table has five permission patterns and one is exercisedLow
2Permission failures never happenA second page table with restrictive PTEs — currently every mapped page is D|A|X|W|R|V, so no permission check can failLow — more PTE entries

4Access-vs-page fault pairPMP denying the page table's own region — the joint case from Step 7Medium — couples two features
5Seven of eight invalidity disjunctsMalformed PTEs, four of which also need an extension turned offMedium — config matrix
6All 48 TLB spansRepeat access, ASID switch, sfence.vma variantsMedium — new generator capability

Rows 1–3 are the same shape as PMP's biggest win: the machinery exists, and the work is varying what the test does with it. The preamble already builds a page table and drops to Supervisor. Adding restrictive PTEs and a different instruction under test reaches step 6 and step 8's failure paths without any new generator capability.
