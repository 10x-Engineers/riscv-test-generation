Execution Plan · R&D Methodology Evaluation

Automated RISC-V Test Generation from Sail

A time-boxed evaluation to decide which methodology to propose for building an automated RISC-V test generator from the Sail Golden Model — not to ship a generator, but to recommend the right architecture, backed by hands-on understanding of each candidate.

Window 21 – 31 Jul 2026 11 working days Owner you + Claude Deliverable recommendation
Decided approach

Evaluate three candidates on two axes — implementation language (Rust vs. Python) crossed with test-generation methodology (symbolic execution vs. concrete oracle) — and produce a single, justified recommendation by 31 July. The Python track keeps ISLA's methodology identical; only the language changes, for industry familiarity and maintainability.

05

Scope & risks, stated plainly

"Python" has two depths, and only the smaller fits the window. Depth (a) — a Python framework over the reused Rust isla engine — is buildable by Day 7; depth (b) — an all-Python symbolic engine on z3-solver — is a multi-week effort. M2 ships (a) and spikes (b) to cost it; M5 recommends whether (b) is worth committing to. If the proposal ultimately wants full-Python maintainability, (a) alone does not deliver it — that gap is named in M5, not glossed.
"Understand every function" of isla-lib is not in scope. It is a large codebase; M1 goes depth-first on the RISC-V execution path already traced for the PMP fix and notes the rest by responsibility.
11 days is comfortable because M4 overlaps M2 and Claude accelerates the docs. If that overlap breaks down, M3 compresses first — M5 can draw its Python findings from M2 directly. Unused slack is reinvested into deeper coverage, not used to pull the deadline earlier.
Explicitly out of scope: a production-ready or fully all-Python generator by 31 Jul; line-by-line reading of isla-lib or the ARM/CHERIoT backends; any AutoTest modifications (M4 is review-only); merging the existing riscv-testgen-sail PRs.
