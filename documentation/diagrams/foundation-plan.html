RISC-V Sail test generation · stage 1

Foundation, Repository by Repository

Everything needed before one instruction can be generated and pass on two simulators. The list is specific because each item has already been hit once — this is scoping, not estimating.

2 · isla — the symbolic library

Make the engine able to run this model 1.5 wk · weeks 1–2 · critical path
TaskDetailDays
Track the Sail releaseThe Sail plugin consumes Sail's Jib IR, whose type definitions and rewrite-pass ordering change between releases. Update against the version pinned at project start1.5
Missing primitivesThe reservation set (load, match, valid, cancel), count_trailing_zeros with its BV support, vector_init, sys_enable_experimental_extensions. Each small; the risk is finding a further one late2
Address widthThe memory overlap check assumes 64-bit addresses. Take the width from the address's own solver-tracked value, so RV32 reads are not mis-sized0.5
Struct-typed vector elementsPMP configuration is vector(64, Pmpcfg_ent) — a vector of bitfield structs. The value encoding has no case for them, so any symbolic PMP access fails. Vector read and update build a per-field conditional instead3
The last row is why PMP is reachable at all. Without it there is no symbolic PMP testing, and PMP is a required RFP item. It is the single highest-value fix in the foundation, and it is why this lane sits on the critical path.

3 · isla-testgen — the generator

Teach the generator about RISC-V 1.5 wk · weeks 2–3 · critical path · needs 1 and 2
TaskDetailDays
Target implementationThe generator's target interface — around thirty methods covering register naming, PC alignment, entry points, exception stop functions, ELF emission3

Concrete boot PCThe engine sets the initial PC by asserting equality at the solver level, which does nothing when the PC is already concrete — as it is here, since init calls reset(). Write the value directly0.5
PC width vs address widthRV32's PC is 32 bits; the model's memory interface uses 64-bit addresses regardless of XLEN. Zero-extend for the fetch0.5
GPR numberingRegisters are assumed to start at zero. x0 is hardwired and not general-purpose, so the interface gains a first-GPR index0.5
IR and ISA configBuild riscv{32,64}.ir with the preserve flags, and the .toml naming the toolchain, PC register and memory regions0.5

5 · framework — orchestration

TaskDetailDays

The sweep runs the ELF, it does not just generate it. Generation not erroring is not proof — a self-targeting jal “succeeds” at generation time and hangs forever when executed.

addi x1, x0, 1 generates from both backends, assembles with the real toolchain, and passes on sail_riscv_sim and on Spike.

Plus: the entry points survive an isla-sail rebuild, verified by a post-build check rather than assumed; and a symbolic PMP register read completes without crashing the engine, which is what proves the struct-typed vector fix landed.

Why the gate is a passing test rather than a working pipeline. Generation completing proves nothing — the failure mode this project keeps meeting is a test that runs and checks nothing. The gate is the narrowest artefact that could not be produced by a broken pipeline.

What this de-risks

Every technical unknown in the engagement resolves in these three weeks, on one instruction, before any breadth is attempted:

UnknownResolved by
Does the engine run this model at all?Lane 2 — primitives and the Sail release
Will upstream accept the entry points?Lane 1 — submitted in week 1, so review starts as early as possible
Can PMP be tested symbolically?Lane 2 — the struct-typed vector fix, checked at the gate
Does the emitter produce a loadable ELF?Lane 3 — run on two simulators, not just linked
Does the oracle path work independently?Lane 4 — it never touches lanes 1–3
Is a generated test capable of failing?The gate — a passing test on an independent simulator
If something here is going to be impossible, it becomes visible in week three rather than in week ten. That is the whole reason the foundation is built as one narrow slice instead of one layer at a time.
Task lists and file names reflect work already carried out once to de-risk this proposal; durations are estimates for repeating it against the model revision agreed at project start.
